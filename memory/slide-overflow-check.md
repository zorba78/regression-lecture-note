렌더된 revealjs HTML에서 내용이 슬라이드(1280×1024) 밖으로 넘치는 곳을 자동으로 찾는 법.

1. 렌더된 HTML을 복사하며 **마지막 `</body>` 앞에만** 측정 스크립트를 주입한다. `str.replace` 전체 치환은 reveal 번들 내부 문자열의 `</body>`에도 들어가 JS를 깨뜨리므로 `rpartition('</body>')`을 쓸 것.
2. CSS로 모든 section을 강제로 보이게 한다(`display:block !important; position:relative !important; height:1024px !important`). 비활성 슬라이드는 `display:none`이라 그냥은 0으로 측정된다.
3. **MathJax 조판이 끝난 뒤에 재야 한다.** `MathJax.Hub.Queue(측정함수)`로 걸고 `--virtual-time-budget=180000`. 동기 실행하면 수식이 원시 텍스트로 잡혀 **거짓 양성**이 대량 발생한다(실제로 9건 중 5건이 허위였음).
4. **세로만 재면 안 된다.** display 수식은 줄바꿈이 없어 가로로 잘려 나가는 사고가 더 흔하다. `getBoundingClientRect().right - section.left` 도 함께 잰다.
5. 가로 측정에는 **약 44~65px의 공통 기준선**이 있다(모든 슬라이드에 나타남). 그보다 큰 값만 실제 문제다.
6. 명령: `chrome --headless=new --no-sandbox --disable-gpu --window-size=1280,2000 --virtual-time-budget=180000 --dump-dom <file> > dom.html`

**2026-08-23 추가: 이 방식이 실패하는 지점.** 슬라이드가 151장으로 늘어난 뒤로는 위 1~3번(모든 section을 CSS로 강제 표시 + 타이머 측정) 방식이 **동작하지 않는다.** 측정 스크립트 자체는 실행되지만(단순 마커는 3초 타이머로 정상 삽입됨), 151개 section을 전부 `display:block; height:1024px`로 펼치면 레이아웃이 너무 무거워 Chrome이 콜백 완료 전에 `--dump-dom` 을 뱉는다. 6장씩 나눠 측정하는 청크 방식도 같은 결과였다. `getBoundingClientRect()` 전수 순회 대신 `document.createRange().selectNodeContents(section).getBoundingClientRect()` 로 section당 1회 호출로 줄여도 마찬가지.

**대안(실제로 쓴 방법):** 변경이 집중된 슬라이드만 골라 스크린샷으로 눈으로 확인한다. revealjs 세로 스택 구조이므로 URL 조각은 `#/h/v` 형식이고, **h = 장 번호 + 1**(예: `#/2/1` = Introduction 첫 슬라이드, `#/2/20` = Introduction 마지막). 명령은 [[tooling-paths-windows]]의 스크린샷 항목 참조. 전수 자동 검사가 필요하면 측정 스크립트를 페이지에 넣지 말고 CDP(Playwright 등)로 슬라이드를 실제 이동시키며 재는 방식을 검토할 것.

**2026-08-27 추가: 실제로 통한 전수 검사(픽셀 방식).** 브라우저 안에서 재는 것을 포기하고 **스크린샷 픽셀만 본다.** 덱 HTML에서 `<section id="..." class="slide level2` 를 정규식으로 뽑아 각 슬라이드를 `msedge --headless --window-size=1280,1024 --screenshot --virtual-time-budget=2500 "file:///...#/<id>"` 로 한 장씩 찍고, 아래쪽 띠(행 1004–1020, x 60–1180)에 흰색이 아닌 픽셀이 있으면 후보로 올린다. x 범위는 왼쪽 햄버거 메뉴와 오른쪽 슬라이드 번호를, 행 범위는 1021–1023의 진행 막대를 피하려고 정한 값이다. 168장에 약 10분. 스크립트는 세션 스크래치패드의 `sweep.py`.

**2026-08-27 재추가: 한 가지 창 크기로만 재면 안 된다.** 위 방식으로 168장 전수 검사를 돌려 "잘림 0장"이라고 보고했는데, 사용자가 실제 모니터에서 찍은 화면에는 잘린 슬라이드가 여럿 있었다. 원인은 CSS의 `vh` 단위였다 — reveal은 고정 캔버스(1280×1024)에 그린 뒤 창 크기에 맞춰 transform으로 확대하므로 슬라이드 안의 `vh`는 **브라우저 창**을 기준으로 계산되고, 하필 1280×1024가 의도한 값과 우연히 일치하는 유일한 지점이었다. **최소 두 크기(예: 1280×1024와 2400×1920)에서 재고, 두 결과의 `last_row`를 캔버스 대비 %로 비교할 것.** 두 %가 같지 않으면 CSS 어딘가에 창 의존 단위가 남아 있다는 뜻이다. 자세한 내용은 [[slide-layout-system]].

이 방식의 **함정 세 가지**:

1. **샷마다 타임아웃을 반드시 걸 것.** `subprocess.run` 에 `timeout=` 이 없으면 종료하지 않는 headless Edge 하나가 전체 검사를 영구히 멈춘다(실제로 3시간 15분 멈췄다). 45초면 충분하고, 실패한 샷은 `NO SHOT` 으로 보고한 뒤 다시 찍으면 대개 정상이다.
2. **꽉 찬 슬라이드는 거짓 양성이다.** 마지막 콜아웃의 아래쪽 테두리가 띠 안에서 끝나면 잉크가 1100 넘게 잡히지만 잘린 것은 아니다(02 "행렬 표기의 필요성"은 행 1007에서 테두리가 끝나고 아래 13행이 비어 있다). **행별 잉크를 찍어 마지막 내용 행을 함께 볼 것** — 잘린 슬라이드는 글자 중간이 잘리므로 행 1020까지 잉크가 이어진다.
3. **흰 내용은 보이지 않는다.** 그림의 흰 여백이 화면 밖으로 나가면 잉크가 0이라 검출되지 않는다. 05 "선택 후 재진단"은 캡션이 통째로 화면 밖에 있었는데도 오래 잉크 0이었다. 그림이 있는 슬라이드는 수치를 믿지 말고 아래쪽을 잘라 눈으로 볼 것.

**해소 방법:** 슬라이드 분할(제목에 부제를 달아 분화. **H2를 그대로 반복하지 말 것** — [[slide-flow-devices]]), `## 제목 {.smaller}`, 긴 수식은 `\begin{aligned}` 으로 줄 나누기, 좁은 column 안에 display 수식을 넣지 않기.

**함정:** qmd에 `aligned` 줄바꿈을 쓸 때 **백슬래시 두 개가 실제로 파일에 들어갔는지 확인할 것.** Python 문자열 이스케이프로 하나만 들어가면 줄바꿈이 통째로 무시되어 한 줄로 붙어 버린다. `\\[2pt]` 같은 간격 지정은 pandoc을 거치며 깨지므로 쓰지 말 것. 관련: [[tooling-paths-windows]]

**2026-08-29: 스크래치패드 스크립트는 더 이상 쓰지 말 것.** 위 방식이 `.claude/skills/run-regression-lecture-note/slidecheck.py` 로 커밋되었다. 세션마다 사라지는 `sweep.py`/`profile.py` 를 다시 만들지 말고 이것을 쓸 것. 위의 함정 1~3과 `--virtual-time-budget=2500` 이 모두 반영되어 있고, `--find` 로 한글 제목에서 슬라이드 번호를 찾는다. 사용법은 같은 폴더의 `SKILL.md`.

**2026-08-29: 가로 넘침 기준선이 25 → 0 으로 바뀌었다.** 오랫동안 "넘침 25장은 정상 기준선"으로 취급했는데, **25장 전부가 CSS 버그 하나였다.** `lecture.css` 의 `.reveal blockquote { width: 100% }` 가 `content-box` 기본값과 겹쳐 실제 폭이 부모 100% + 패딩 1.6em + 테두리 5px 이 되면서 **음영 배경이 슬라이드 오른쪽 밖으로 넘쳐 나오고 있었다.** 인용문을 `.highlight-box`(폭 미지정)로 바꾸면서 사라졌다. 이제 넘침이 잡히면 전부 실제 결함이다. 기준선을 다시 올리지 말 것.

**2026-08-29: 픽셀 검사가 못 잡는 결함이 있다.** 수식이 조판되지 않고 `$$...$$` 리터럴로 나와도 잘리지도 넘치지도 않으므로 `clipped 0 / overflow 0` 으로 통과한다(03 "회귀계수의 분산과 공분산"이 그랬다). **그림·수식이 있는 슬라이드는 수치를 믿지 말고 스크린샷을 눈으로 볼 것** — 위 함정 3과 같은 교훈이다. `$$` 개수 홀짝 검사가 이 유형을 싸게 잡아낸다.
